# P4-006 — BlueZ NAP lifecycle adapter

P4-006 implements the server side of Bluetooth PAN/BNEP through BlueZ `org.bluez.NetworkServer1` on a selected local Bluetooth adapter.

## Selected API

BlueRoute uses BlueZ directly for NAP registration:

- service: `org.bluez`
- object: `/org/bluez/{hci*}`
- interface: `org.bluez.NetworkServer1`
- start: `Register("nap", bridge)`
- stop: `Unregister("nap")`

BlueZ registers the NAP SDP service and accepts incoming PANU BNEP sessions. For each accepted session BlueZ creates a BNEP network interface and adds it to the Linux bridge supplied to `Register`.

The supplied bridge must already exist. P4-006 deliberately does **not** create bridges, assign IP addresses, configure DHCP/DNS, or own NetworkManager profiles. Those operations belong to the network-backend/IP layers beginning with P4-007. Keeping those responsibilities separate allows `PanBackend` to remain independent of NetworkManager.

Accordingly, the backend-neutral NAP start boundary is:

```rust
start_nap(adapter, bridge) -> PanAttachment
```

The returned NAP service attachment identifies the supplied bridge and has no remote peer because it represents the local NAP service rather than one client session.

## NAP ownership and lifecycle safety

`NetworkServer1` does not expose a query that identifies which D-Bus client owns a registered NAP role. Calling `Unregister("nap")` blindly could therefore tear down state registered by another process.

`BluezBackend` keeps bounded local ownership state for NAP registrations. The state records:

- adapter;
- supplied bridge;
- BlueZ's current unique D-Bus owner name;
- lifecycle phase (`Registering`, `Active`, or `Stopping`).

Repeated `start_nap` for the same adapter, bridge, and BlueZ service instance is idempotent. Starting the same locally owned NAP on a different bridge fails with `InvalidState` rather than silently moving it.

`stop_nap` calls BlueZ `Unregister("nap")` only for a registration owned by this backend against the same BlueZ service instance. If BlueZ restarted, its unique D-Bus owner changes and BlueZ has already removed registrations tied to the old D-Bus client/service lifetime; BlueRoute clears its stale local state without issuing an unregister against the new instance. Repeated stop after the desired state is already absent succeeds.

This is deliberately fail-closed. A new BlueRoute process does not adopt or unregister an unknown pre-existing NAP registration merely because BlueZ reports `AlreadyExists`.

## PAN client attach/detach observation

BlueZ `NetworkServer1` does not publish a dedicated client-attached/client-detached signal. The authoritative Linux data-plane state is the set of BNEP interfaces that BlueZ inserts into the registered bridge.

`subscribe_nap_events` therefore reconciles the live bridge membership under:

```text
/sys/class/net/<bridge>/brif
```

and filters members to Bluetooth network devices by their sysfs `DEVTYPE=bluetooth` uevent metadata. This identifies the actual post-udev interface name, so event reporting is not tied to a `bnepN` naming assumption.

The subscription retains one current sorted set and a bounded queue of the current diff. It emits backend-neutral events:

- `NapEvent::ClientAttached(PanAttachment)`;
- `NapEvent::ClientDetached(PanAttachment)`.

Client attachments use `PanRole::Nap`, the live BNEP interface handle, and currently leave `peer` as `None`. P4-006 observes the NAP data-plane attachment itself; correlating a server-side BNEP netdev to a higher-level BlueRoute node identity is a separate topology/membership concern.

The bridge set is reconciled every 250 ms. This avoids unbounded history and does not depend on a particular udev/BlueZ signal ordering. Extremely short-lived sessions that both attach and detach entirely between polls may not produce a pair of events; persistent desired state still converges on the next poll.

## Errors and capability reporting

The adapter validates that the supplied interface exists and is a Linux bridge before calling BlueZ. Common failures are mapped into typed core errors:

- powered-off adapter -> `AdapterDisabled`;
- `NetworkServer1`/NAP unavailable -> `CapabilityUnavailable`;
- authorization denial -> `CapabilityUnavailable`;
- another NAP registration already exists -> `InvalidState`;
- malformed/rejected protocol arguments -> `ProtocolError`;
- other NAP setup/teardown failures -> `PanFailure`;
- unavailable D-Bus/BlueZ transport -> `BluezUnavailable`.

Low-level D-Bus details remain in diagnostics.

## Hardware probe

P4-006 includes `bluez_nap_probe`. It requires an already-created Linux bridge but performs the Bluetooth NAP lifecycle through the Rust adapter.

Example test setup on the NAP machine:

```bash
sudo ip link add br-blueroute-test type bridge
sudo ip link set br-blueroute-test up
cargo run -p blueroute-linux --example bluez_nap_probe --locked -- br-blueroute-test 600
```

If another application or NetworkManager profile already registered the NAP role on that adapter, stop that registration first; BlueRoute intentionally refuses to take it over.

The probe:

1. selects the first powered adapter;
2. registers `nap` through `PanBackend::start_nap`;
3. subscribes to client attach/detach state;
4. prints live BNEP client interface names during a bounded hold window;
5. calls `stop_nap` twice to exercise idempotent cleanup.

For hardware acceptance, use the P4-005 PANU probe from the second Linux node while this Rust NAP probe is running. Configure temporary test IP addresses externally on the NAP bridge and PANU interface, prove ordinary traffic traverses BNEP, and capture attach/detach output. CI cannot satisfy this physical acceptance criterion.

After testing, remove the temporary bridge only after the NAP probe has stopped:

```bash
sudo ip link del br-blueroute-test type bridge
```

## Scope boundary

P4-006 owns Bluetooth NAP registration, accepted BNEP client observation, and NAP teardown. P4-007 owns the production network-backend lifecycle needed to create/configure BlueRoute-owned bridge/addressing state without shell-command parsing.
